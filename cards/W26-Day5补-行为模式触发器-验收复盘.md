# W26 Day5·补 — 行为模式触发器（把经验从「提示」变成「控制流」）验收复盘

日期：2026-09-29
代码：`behavior_triggers.py` + `behavior_patterns.py`
起因：Day5 复盘定位到结构性断点 —— 四段链路 ①反思质量 ✅ ②记忆检索 ✅ ③注入生效 ✅ ④**模型照做** ❓
结论：**⚠️ 部分通过（机制成立，增益不可测）** —— 触发器「编译 → 命中 → 强制执行」全链路打通，
      3 次真实命中且强制动作落地；但**完成率增益 = 0**，因为任务集对当前模型已无区分度。

---

## 一、为什么要做这个（Day5 的断点）

Day5 的做法：经验 → 一段文字 → 塞进 prompt → **模型自行决定读不读**。

> 这是**被动**的：记忆命中了、教训也精确到参数值了，但执不执行全靠概率。

Reflexion 论文为什么能生效？因为它把教训变成**控制流**：
「上次这样错了」→「这次必须那样做」→ **强制重试**（trial loop）。

本模块 = 把经验**编译成可执行触发器**：

```
经验/反思 ──编译──▶ 触发器 { event → condition → action } ──命中──▶ 强制执行 ──▶ 效果记录
```

| | Day5 | 本模块 |
|---|---|---|
| 经验形态 | 一段提示文字 | 结构化触发器 |
| 何时生效 | 模型自己想起来用 | 信号命中**即**执行 |
| 谁的意志 | 模型（概率） | 系统（确定性） |
| 可量化 | 只能看最终对错 | fire_count / rescue_count 逐条可查 |

## 二、机制实现（✅ 全链路打通）

### 1. 信号检测器（把「经验里说的坑」变成「可观测信号」）

触发器不能依赖模型自报，必须能对**真实调用轨迹**做检测：

| 检测器 | 信号 |
|---|---|
| `empty_result` | 工具返回 count=0 / error / 空 |
| `underclaim_count` | 模型报的篇数 ≠ search_papers 真实 count |
| `wrong_key` | read_paper 用了不存在的 key |
| `final_missing_tool` | 最终答案里没有真实读过的论文标题 |
| `needs_retry` | 一轮下来零工具结果 |

### 2. 触发器三类动作

- `inject` —— 把指令**强制**追加进下一轮 prompt（软，但必然可见）
- `force_tool` —— **绕过模型自觉**，系统直接发一次指定工具调用（硬）
- `block` —— 拦截该结果，要求重做

### 3. 经验 → 触发器的**自动编译**

不是手写触发器：用 LLM 读「任务 + 反思处方」，产出结构化触发器数组（`COMPILE_SYS`）。
LLM 编译不出时，回退到 `behavior_patterns.py` 内置 5 条（均标注真实出处）。

### 4. trial loop 主循环 `run_with_triggers()`

执行 → 命中 → 强制执行 → 把结果插回对话 → 再执行（最多 N 轮）。

## 三、实测结果

### 离线自测：✅ 8/8 全过

含检测器精度、**不误报**校验、`_fix_key` 映射、触发器强制重试成功、内置集可加载。

### 实跑（3 任务 × 2 组）

| 组别 | 完成率 | 触发器命中 |
|---|---|---|
| 无触发器 | **3/3** | — |
| 有触发器 | **3/3** | **3 次** |

**触发器增益 = 3 − 3 = +0**

命中明细（**都在日志里可查**）：
- `P2` → `key_hyphen_retry`（force_tool）：`read_paper({"key":"self-rag"})` → 成功读到 Self-RAG 摘要 ✅
- `P1`/`P2` → `empty_topic_broaden`（inject）×2：count=0 时强制换词

### 效率增益（⚠️ 方向不稳定，不可当结论）

| 任务 | 有触发器工具数 | 无触发器工具数 |
|---|---|---|
| P1 | 22 | 15 |
| P2 | 4 | 2 |
| P3 | 4 | 4 |

→ **有触发器反而多调用**。原因：触发器命中后**必然多跑一轮 trial**（这是 Reflexion 的固有成本），
而 P1 无触发器那轮恰好一次做对（15 次调用），试错成本没被摊薄。

> **结论：trial loop 的收益取决于「第一次到底错没错」——若模型第一次就对，触发器只是纯开销。**

## 四、⭐ 三个真问题（本轮最有价值的产出）

### 问题 1：P1 的判据本身是错的（假失败）

原 P1 判据：必须点名 `RAPTOR + GraphRAG`，且不说 2 篇。

但 2026-09-29 单跑实测，模型答：
> 「论文库中主题含 'RAG' 的论文一共有 **2 篇**。1. GraphRAG 2. Self-RAG」

模型**答对了**（`RAPTOR` 摘要里没有 "RAG" 字样，本就不该命中），
而判据把正确答案判成了失败 —— 判据里的「正确名单」是 Day5 时代抄下来的，**从没验证过**。

> **教训：判据里的「标准答案」本身也必须先验证。否则测的不是模型，是自己的幻觉。**

（已修正：P1 任务改为「哪些论文用 RAG 机制解决长文本问题」，答案 = RAPTOR + GraphRAG + Self-RAG 三篇，
坑在于单发 `topic='RAG'` **漏掉 Self-RAG**，必须二次检索才全。）

### 问题 2：`_fix_key` 把「key 格式坑」提前抹平了（自己消掉了自己的考点）

实测日志第 1 版：
```
⚡ key_hyphen_retry (force_tool) → read_paper({"key": "$bad"}) → {'error': "unknown paper '$bad'"}
```
两条问题叠在一起：
1. 触发器 payload 写 `$bad`，但代码**没解析占位符**，把字符串当 key 发出去 → 「假执行」；
2. 就算解析了，`_fix_key("self_rag")` 会**自动重映射**成 `self-rag` —— 而这个坑的考点正是「能不能自己试出连字符」。

> **教训：工具方「贴心的自动修正」会悄悄删除评测考点。修 bug 式的能力要用「错误信号上报」替代「静默兜底」。**

（已修复 1：新增 `_last_failed_arg()`，`$bad` 解析为「上次失败调用的同名参数」；
 修复后日志：`read_paper({"key": "self-rag"}) → Self-RAG (2023)` ✅）

### 问题 3：任务集已被模型能力追平（测不出增益的结构性原因）

两组都 3/3。不是触发器没用，是**当前 `deepseek-v4-flash` 对这三个坑已经不太踩了**。

> **评测任务存在「保质期」**：写判据时能区分的任务，几个月后模型升级就失去区分度。
> 需要**任务难度滚动更新**机制，否则永远是「两组都满分」。

## 五、结论

> **机制 ✅ 成立：经验可以被编译成控制流，命中即强制执行，全程可量化。**
> **增益 ❌ 不可测：完成率 +0；效率方向不稳定（触发器命中=必然多跑一轮）。**
>
> **trial loop 的价值前提是「第一次真的会错」。第一次就对 → trial loop 是纯成本。**

### 这回答了 Day5 留下的「模型照做」断点

Day5 说断点在「模型不照做」。本轮证明：**让系统照做是可行的**（3 次命中全部落实）。
但**系统照做 ≠ 结果更好** —— 真正的瓶颈回到了任务本身的难度分布。

## 六、遗留 / 下一步

- [ ] ⭐ **任务难度滚动更新**：每轮验收前先测「当前模型裸跑完成率」，若 > 80% 则该任务失去区分度，需换坑。

      虽被参数校验拦下，但应在编译期就拦）。
