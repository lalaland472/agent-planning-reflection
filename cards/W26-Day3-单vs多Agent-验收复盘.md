## 三、三个关键发现

### 1. 审查者真在干活：3/3 全部打回返工 ⭐
- T1：执行者想"凑 3 篇"，Critic 对照清单发现库内只有 2 篇 → 打回 → 改为如实说明库内不足；
- T3：Critic 发现"method 主题检索 0 条"未交代 → 打回 → 补上"该主题无论文，以 RAG 替代"。

→ **多 Agent 的核心价值 = 独立复核，把单 Agent 会滑过去的失败摊开。**

### 2. 质量差全部来自「完整性」这一维度
single 三次固定 7.5，丢的 2.5 分就是"不逐条交代子目标"。multi 因有清单+审查逼着交代而拿满。
→ **多 Agent 不是"更聪明"，而是"更守规矩"。**

### 3. 成功率无差异（都是 3/3）
任务太简单，两种模式都轻松通过 → **多 Agent 买不到成功率，只买到复核能力。**

---

## 四、结论（验收核心）

> **多 Agent 买的是「复核能力」，不是「成功率」。**

| 场景 | 值得？ |
|---|---|
| 输出需独立复核 / 失败必须暴露 | ✅ 值得 |
| 步骤固定、答案明确的简单任务 | ❌ 不值得（token 2.89x 无收益） |
| 成本 / 延迟敏感 | ❌ 不值得 |
| 单 Agent 会做错的困难任务 | ⚠️ 待验证（本次未覆盖，留给 W27 AgentBench） |

**工程建议**：默认单 Agent；仅当「需要复核」或「失败必须暴露」才上多 Agent；若上，Critic 是最值得保留的一环。
