## 二、设计要点

### 短期记忆：滑窗 + LLM 摘要压缩
- `max_turns=4` 触发，`keep_recent=3` 保留最近消息；
- 旧消息经 LLM 压成摘要，**新旧摘要叠加**（不覆盖，否则长任务会丢早期信息）；
- 压缩次数 `compress_count` 可观测，便于验收。

### 长期记忆：BGE + FAISS 存经验
- 经验 = `(任务, 结果, 反思)` 三元组，BGE 编码后存 `IndexFlatIP`；
- 经验量少（数十条），**不需要 HNSW**，Flat 精确检索更合适（与 rag-kb 主索引用 HNSW 的场景相反）；
- **query 加 BGE 官方指令前缀**（`为这个句子生成表示以用于检索相关文章：`），提升检索质量；
- `(task, outcome)` 哈希去重，防止重复沉淀；
- 人类可读镜像 `experience_notes.md`，便于人工核查。

## 三、⚠️ 反直觉发现：短历史下「摘要压缩」反而涨 token

| | 原始 | 压缩后 |
|---|---|---|
| 上下文规模 | 201 字 | **221 字（110%）** |

**原因**：摘要是 LLM 生成的自然语言，本身就有开销；只有历史足够长（数十轮）时，压缩的收益才盖过摘要成本。

→ **教训：摘要压缩不是无条件省钱**。工程上应设**最小压缩阈值**（如 `len(old) > 500` 才压），否则短会话压缩是负优化。本次测试数据太短，属边界情况，但结论对参数调优有直接指导意义。

## 四、另一个发现：语义检索不被错误数据带偏

测试时故意写入一条错误经验（`add(2023,2024)=4047`），想验证检索是否会被污染。结果：查询"帮我算一下 2023 加 2024"仍**正确命中计算类经验**（0.647）。

→ **检索是按语义匹配任务类型，不靠关键词碰运气**，单条错误内容不会污染检索路径（但会污染注入内容，故 `remember` 应有质量门禁）。

原卡片列了 4 项遗留，本次关闭 3 项（第 4 项 D5 主循环接入见下）：

| 遗留 | 实现 | 验证 |
|---|---|---|
| ① 最小压缩阈值 | `ShortTermMemory(min_compress_chars=500)`：除消息条数外，**待压内容**也须 ≥ 阈值才触发；`skipped_compress` 可观测 | ✅ 短内容（103字）跳过 / 长内容（450字）触发 |
| ② 经验质量门禁 | `_bad_reflection()`：写入前拒收 空教训 / `(解析失败)` 占位 / 过短（<8字） | ✅ 4/4（含正常教训应写入的反例） |
| ③ 经验过期/版本戳 | `remember(..., scope=)` + `recall(scope=)` + `expire(scope)`：经验带环境版本戳，只召回同版本 | ✅ v1 命中 1 条 / v2 命中 0 条 / expire 作废正常 |

### ⚠️ 补齐过程中踩到的两个坑（可复用教训）

**坑 1：scope 的「向下兼容」会反向咬人**
为兼容旧数据，`scope=""` 的经验被视为「无版本约束」，会匹配任何 scope。
结果在**同一目录混存带/不带 scope 的经验**时，`recall(scope="v2")` 会误命中旧经验。
→ 修正：测试必须用**独立干净库**隔离；并在代码注释里写清这个兼容语义。

**坑 2：测试数据撑不到自己的阈值 = 假失败**
最小压缩阈值的测试一开始全挂，查下来是**测试样本只有 103 字**、够不到 500 的阈值。
机制没问题，是用例写错。
→ 修正：断言前先打印「待压字数 vs 阈值」，用足量数据验证阈值**两侧**行为。

> **教训：验证一个「阈值型」机制，必须同时测阈值两侧，且样本要真的能跨过阈值。**
